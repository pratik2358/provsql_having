\section{Implementation and Experiments}
\label{sec:implementation_experiments}
\subsection{Implementation}
We implemented within ProvSQL, in C++, \textsc{ValidCount},
\textsc{ValidSum}, the closed forms of Proposition~\ref{prop:algorithms}
for \sql{MIN}, \sql{MAX} and \fakesql{PICKFIRST}, and brute-force
enumeration otherwise. Beyond these algorithms, the implementation prunes
with the bounds of Proposition~\ref{prop:algorithms}: in an absorptive
m-semiring, for the upward-closed comparisons (\sql{COUNT(*) >= k},
\sql{> k}, \sql{SUM(a) >= c}, \sql{> c}) only the minimal valid worlds
are generated, and when every non-empty world is valid the provenance
collapses to the $\oplus$ of the annotations of the group. A \emph{range
check} first compares the threshold with the smallest and largest values
the aggregate can take over the worlds (e.g., for \sql{SUM}, the sums of
the negative and of the positive values) and returns $\mathbb 0$ when
the comparison is unsatisfiable. For \sql{SUM}, the table of the dynamic
programming is bounded by the comparison constant when values are
nonnegative integers, and sums not yet reachable are skipped; negative
values and tables beyond $10^7$ entries fall back to enumeration.
For probability evaluation, we also implemented the algorithms presented
in Proposition~\ref{prop:agg-cmp-poly-prob}.
Finally, while constructing semiring provenance expressions, we fold standard
(m-)semiring identities: multiplication by $\mathbb 1$, addition or
multiplication by $\mathbb 0$, etc.

\subsection{Experiments}
To test our implementation and validate the practical feasibility of the
\sql{HAVING} semantics, we ran experiments on a probabilistic image-retrieval database. Following the method
in~\cite{yunus2025using}, the database is built from object-detection
output over a dataset derived from COCO 2017~\cite{lin2014microsoft}: for each
image, YOLOv5~\cite{ultralytics2021yolov5} detects objects,
and each detected object is stored as one tuple in relation \sql{dataset} with
a unique identifier \sql{id}, the image identifier \sql{img}, the object
class \sql{obj}, and a probability derived from the detector
confidence score. These object annotations are treated as independent
probabilistic facts. The database contains $239{,}377$ images and $1{,}570{,}565$
object annotations.

We compare execution times in ProvSQL for: (i)~provenance tracking (with
production of a symbolic formula representing the provenance); and
(ii)~probability computation of a \sql{HAVING} query with comparisons of
the form \sql{COUNT(*) >= k} or \sql{COUNT(*) <= k} to find images with
at least (or at most) $k$ objects for a given class, for our
possible-world semantics against the equivalent self-\sql{JOIN} version
(see Theorem~\ref{th:correctness}).
Note that this is the exact set-up of \cite{yunus2025using}, where
authors had to use the \sql{JOIN} version as nothing else was available.

We choose a specific object class (72, \emph{refrigerator}).
In our experiments we vary the scalar~$k$ of the queries from 0 to 15
(the maximum number of refrigerators detected in an image is 13).
The exact queries we ran, along with their \sql{JOIN}-rewrites, are presented in
\hyperref[sec:appendix_impl_experiments]{Appendix~\ref*{sec:appendix_impl_experiments}}. For probabilistic query
evaluation, we use the default ProvSQL pipeline: a cost-based chooser
selects, for each provenance circuit, the cheapest exact method it
estimates applicable, among linear-time evaluation of read-once
circuits, exhaustive enumeration of the possible worlds of circuits with
very few inputs, inclusion--exclusion over the clauses of a small DNF,
tree decompositions of small treewidth, in-process compilation to
d-trees and, as a last resort, an external knowledge compiler
(d4~\cite{DBLP:conf/ijcai/LagniezM17}); a method that turns out slower
than estimated is abandoned for the next one. In our experiments, the
circuit of a group has at most 13 inputs; for the \sql{HAVING} queries
the chooser settles on world enumeration, inclusion--exclusion or
read-once evaluation, whereas the larger circuits of the \sql{JOIN}
rewritings also require tree decompositions, d-trees and, for some
values of~$k$, d4.

For each $k$, every query was executed $3$ times on a desktop computer
(Intel Core i7-12700, 64~GB of RAM) running Ubuntu 22.04, with PostgreSQL
18.6; the figures report the mean of the three runs, with error bars at
one standard deviation, on a logarithmic scale. We report the execution
time measured by \sql{EXPLAIN ANALYZE}, which excludes query planning. We
disabled PostgreSQL's genetic query optimizer, which by default replaces
exhaustive join ordering from 12 relations onwards: for the self-\sql{JOIN}
rewritings with $k \geq 12$, the join order it selected applied the
``\sql{id >}'' chain late, the intermediate results blew up, and the queries
exceeded a five-minute timeout, whereas the exhaustive planner finds an
order for which execution stays around 3 seconds (its planning time,
up to 20 seconds for $k = 15$, is not included in the reported times).

Figure~\ref{fig:prov_only_times_ge} and Figure~\ref{fig:prov_only_times_lt} report query
execution times including the materialization of a textual representation
of a provenance formula, comparing our possible-world semantics
with the corresponding \sql{JOIN}-based rewriting. During execution, our semantics constructs
a provenance circuit with a \emph{comparison gate} representing the aggregate comparison. The
possible-world semantics is triggered at the semiring evaluation level,
by instantiating the formula pseudo-semiring (\sql{sr_formula})
in ProvSQL. For provenance computation alone, the running time of our
semantics remains stable as $k$ varies, between $0.2$ and $0.6$ seconds;
for ``\sql{COUNT(*) >= k}'' it even decreases slowly with~$k$, as the
range check discards more groups. For this query, the \sql{JOIN}-based
rewriting is faster for $k \leq 4$, and then becomes slower than the
\sql{HAVING}-based semantics, its cost growing with the number of joins
up to $13$ times that of our semantics -- queries with a large number
of joins can be slow for the query evaluator. For the
``\sql{COUNT(*) <= k}'' query, the \sql{JOIN}-based rewriting (which
includes a non-monotone \sql{EXCEPT}) is again cheaper for $k \leq 2$,
but becomes up to $6$ times more expensive than our semantics for larger
values of $k$. Thus, for provenance computation alone, the main
observation is the stability of the runtime cost, which pays off as $k$
increases.

The difference becomes much more pronounced in Figure~\ref{fig:prob_eval_times_ge} and
Figure~\ref{fig:prob_eval_times_lt}, where probability evaluation is included in addition
to query execution and provenance computation. In these experiments,
we compare three different probability computation modes: \sql{HAVING}
semantics with the Poisson-binomial CDF optimization for counting independent events
of Proposition~\ref{prop:agg-cmp-poly-prob}, plain \sql{HAVING} semantics
(the same optimization disabled, so that the provenance circuit goes through
the general probability pipeline), and
\sql{JOIN} rewriting; recall that probability evaluation is, in
general, \#P-hard. The first two remain efficient for all values of~$k$,
between $0.2$ and $0.5$ seconds, and within a few percent of each other:
with at most $13$ objects per image, the DNF of valid worlds of a group
is small enough for the general pipeline to evaluate it by world
enumeration or inclusion--exclusion, so that the closed form of
Proposition~\ref{prop:agg-cmp-poly-prob} brings no measurable gain on
this dataset; it would on groups with more tuples, where the DNF
has~$\binom{n}{k}$ clauses. The \sql{JOIN} rewriting is again cheaper for
$k \leq 3$, then becomes up to $17$ times slower than our semantics for
the monotone $\geq k$ case and up to $7$ times slower for the $\leq k$
case, since it pays, in addition to the joins, the probability
evaluation of larger circuits, some of which require tree decomposition
or knowledge compilation. Note also that the \sql{JOIN} rewriting is
unable to exploit the fact that the query becomes vacuously true or
false when $k$ is higher than the number of objects in the images, which
both our implementations can.

\begin{toappendix}
  \section{Material for Section~\ref{sec:implementation_experiments}
  (Implementation and Experiments)}
\newcommand{\quotedzero}{\PYG{l+s+s1}{\apos$\mathbb{0}$\apos}}
\label{sec:appendix_impl_experiments}

We present the query templates used for the experiments of
Section~\ref{sec:implementation_experiments}. They are SQL queries using
the functions of the ProvSQL extension of PostgreSQL (\sql{provenance()}, \sql{sr_formula},
\sql{probability_evaluate}, etc.)

The \sql{HAVING}-based template is the following, its condition being
instantiated with \sql{COUNT(*) >= k} or with \sql{COUNT(*) <= k}:
\newcommand{\apos}{\texttt{\textquotesingle}}
\begin{minted}[fontsize=\small, breaklines, escapeinside=||]{postgresql}
SELECT * FROM (
  SELECT img, sr_formula(provenance(), 'image_mapping') AS prov
  FROM dataset
  WHERE obj = c
  GROUP BY img
  HAVING COUNT(*) >= k  -- or:  HAVING COUNT(*) <= k
) sub WHERE prov <> |\quotedzero|;
\end{minted}

For probability evaluation, the call to \sql{sr_formula} in the
projection is replaced by \sql{probability_evaluate(provenance())}, and
the final filter, which
discards the images whose provenance simplifies to~$\mathbb 0$, becomes
\sql{prov > 0}, discarding those whose probability is~$0$; under the
\sql{HAVING} semantics, these are the images for which the aggregate
comparison holds in no possible world.

The equivalent self-\sql{JOIN} rewriting for the ``\sql{>= k}'' case uses
a $(k{-}1)$-fold self-join, with the
``\sql{id > }'' chain ensuring distinct matching tuples:
\begin{minted}[fontsize=\small, breaklines, escapeinside=||]{postgresql}
SELECT * FROM (
  SELECT img, sr_formula(provenance(), 'image_mapping') AS prov
  FROM (
    SELECT DISTINCT d1.img
    FROM dataset d1
    JOIN dataset d2 ON d2.img = d1.img AND d2.obj = c AND d2.id > d1.id
    ...
    JOIN dataset dk ON dk.img = d1.img AND dk.obj = c AND dk.id > d|\(_{k-1}\)|.id
    WHERE d1.obj = c
  ) AS t
) sub WHERE prov <> |\quotedzero|;
\end{minted}

The ``\sql{<= k}'' case is non-monotone and is rewritten as
``at least one match''~\sql{EXCEPT}~``at least~$k+1$ matches'':
\begin{minted}[fontsize=\small, breaklines, escapeinside=||]{postgresql}
SELECT * FROM (
  SELECT img, sr_formula(provenance(), 'image_mapping') AS prov
  FROM (
    SELECT DISTINCT d1.img
    FROM dataset d1
    WHERE d1.obj = c
    EXCEPT
    SELECT DISTINCT d1.img
    FROM dataset d1
    JOIN dataset d2 ON d2.img = d1.img AND d2.obj = c AND d2.id > d1.id
    ...
    JOIN dataset d|\(_{k+1}\)| ON d|\(_{k+1}\)|.img = d1.img AND d|\(_{k+1}\)|.obj = c AND d|\(_{k+1}\)|.id > dk.id
    WHERE d1.obj = c
  ) AS t
) sub WHERE prov <> |\quotedzero|;
\end{minted}
The same projection / zero-filter substitution applies to obtain the
\sql{probability_evaluate} variants of both \sql{JOIN} rewritings.
